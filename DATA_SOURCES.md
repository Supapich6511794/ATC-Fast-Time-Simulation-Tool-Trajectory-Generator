# Where every dataset in this project comes from

Six independent sources feed the trajectory generator. They are easy to confuse,
because several describe the same airspace and two of them ship files with
identical names. This document says which file comes from where, what it is
trusted for, how to refresh it, and where the sources overlap.

**Status as of 2026-09-20:** the AIP scrape (source A) is on AIRAC **2609**
(effective 03 Sep 2026; re-ingested 2026-09-20). The AIXM export (source B) and
everything derived from it is still on **2608** (06 Aug – 02 Sep 2026) —
refreshing it needs a new SWIM export. See [Currency](#currency) below.

---

## At a glance

| Source | What it authoritatively provides | Refreshable? |
|---|---|---|
| **A. AIP Thailand** (CAAT eAIP, scraped) | Waypoints, airways, airports, predefined routes, threshold elevations, sector vertical limits | Yes — from the public eAIP |
| **B. AIXM 5.1.1 export** (SWIM) | SID/STAR/approach procedures, route-segment direction, P/R/D activity times | Needs your own export (licensed) |
| **C. ARINC 424 "DFD" navdata** (GeoJSON layers) | Runways, gates, airport table, airway point layers, holding patterns | Pre-existing project layers |
| **D. Thai APM** | Climb/descent **rates** per aircraft type | Regenerated by Thai APM |
| **E. CAT062 surveillance** | Runway-use climatology, traffic profiles, validation references | From the local traffic DB |
| **F. Operational assumptions** (in code) | Speed schedules, service ceilings, separation minima | Hand-maintained |

## A. AIP Thailand — the CAAT eAIP, scraped

Public HTML at `https://aip.caat.or.th/{AIRAC}-AIRAC/html/eAIP/`, parsed into
JSON caches. **This is the authoritative source for the enroute network.**

| AIP section | What is taken | Lands in |
|---|---|---|
| ENR 4.4 — Name-Code Designators for Significant Points | 344 waypoint coordinates | `aip_VT.json` → `waypoints` |
| ENR 3.1 — Lower/Upper conventional ATS routes | Airway → ordered fix sequence | `aip_VT.json` → `airways` (135) |
| ENR 3.3 — RNAV routes (incl. Y8) | Airway → ordered fix sequence | same |
| AD 1.3 + AD 2.x | 47 airports, elevations, transition alt/level | `aip_VT.json` → `airports` |
| ENR 1.10 — Flight planning | Predefined FROM / TO / ROUTE entries | `aip_routes_VT.json` |
| AD 2 — per-runway thresholds | Threshold elevations | `thai_aip_ad2_thr_elevations.csv` |
| ENR 2.1 + ENR 5.1 | Sector **vertical limits** (attributes only) | `sectors_corrected/*.geojson` |

**Scripts:** `scripts/ingest_aip.py --airac YYYY-MM-DD`,
`scripts/ingest_aip_routes.py --airac YYYY-MM-DD`.

**This is what actually flies a filed route.** When the server expands
`BKK A1 POTEV` into fixes, `_expand_airways` (`api/server.py`) reads the AIP
airway sequences — not AIXM.

The sector corrections are documented in
`web/public/data/sectors_corrected/CORRECTIONS.md`: vertical limits were fixed
against ENR 2.1 / 5.1 at cycle 2026-07-09 and cross-checked against MATS Part II
(AEROTHAI `QP-ACC.MK-001` Rev.12). **Geometry was not modified** — only
attributes, verified byte-identical after edit.

## B. AIXM 5.1.1 — the SWIM export

`aixm_export_2608_VT_v5.1.1.xml` (36 MB), exported 2026-09-02 for cycle 2608:
5 581 selected features, 14 155 after reference closure.

> **Licensing.** Navigraph/Jeppesen-derived commercial data. Internal and
> demonstration use only, **not for redistribution** — which is why the XML is
> gitignored while the layers built from it are committed, so the app runs from
> a clean clone. Refreshing needs your own copy of the export.

Three scripts read it; nothing reads the XML at runtime.

### B1. Terminal procedures — `scripts/ingest_aixm_procedures.py`

Reads `StandardInstrumentDeparture`, `StandardInstrumentArrival`,
`InstrumentApproachProcedure` and their `ProcedureTransition` →
`ProcedureTransitionLeg` chains, resolving each leg to `DepartureLeg` /
`InitialLeg` / `ArrivalLeg` / `FinalLeg` / `MissedApproachLeg`. Per leg it takes
the ARINC path terminator, magnetic course, altitude/speed limits, turn
direction, RNP and `flyOver`, and **rebuilds the waypoint description code**
(IAF / IF / FAF / MAPt) from each fix's position in its transition, because AIXM
does not carry that column.

Output keeps the old ARINC-424 "DFD" schema so nothing downstream changed:

| File | Features |
|---|---|
| `aixm/sid_waypoint.geojson` / `sid_line.geojson` | 3 425 / 544 |
| `aixm/star_waypoint.geojson` / `star_line.geojson` | 939 / 217 |
| `aixm/pbn_waypoint.geojson` / `pbn_leg.geojson` | 1 279 / 387 |
| `aixm/ils_wp.geojson` / `ils_leg.geojson` | 3 679 / 1 042 |

The `HM`/`HF`/`HA` hold legs inside these also feed the approach-area holding
patterns in `web/lib/holdings.ts`.

### B2. Route-segment direction — `scripts/ingest_aixm_route_segments.py`

Reads `RouteSegment` → `availability/RouteAvailability/direction` plus each
segment's endpoints and level band → `aixm/route_segments.json`. **751 segments,
229 of them one-way** (146 FORWARD, 83 BACKWARD) — a third of the enroute
network. Used only by the PDR wrong-way-airway check
(`web/lib/pdr/airwayDirection.ts`); it never feeds trajectory generation.

### B3. Restricted-airspace activity — `scripts/extract_aixm_restricted_areas.py`

Reads every `Airspace` of type P/R/D/TRA and its
`AirspaceActivation/timeInterval/Timesheet`: day or day-span (`ANY`/`HOL`),
clock or solar window (`SR`/`SS`), and `excluded=YES` sheets that subtract time.
Plus the free-text `activity:` LinguisticNote for schedules that do not reduce
to a timesheet ("Notified by NOTAM"). 95 areas →
`aixm/pdr_activity.json` (machine-readable) and `aixm/prdt_areas_2608.csv`
(human-readable).

**Only the times come from AIXM** — see [Overlaps](#overlaps) §2.

## C. ARINC 424 "DFD" navdata — the GeoJSON GIS layers

The project's pre-existing layers, in the Navigraph "DFD" column layout
(`waypoint_identifier` / `waypoint_latitude` / `seqno` / `area_code` …). Coded
terminal procedures are **not** in the CAAT eAIP — it publishes them only as
charts — which is why this family exists alongside the AIP scrape.

| File | Contents |
|---|---|
| `airway_waypoint.geojson` | Airway points with route id, level and direction restriction |
| `airways/airway_vor.geojson` | 2 801 VOR/DME navaid points |
| `airways/airways_reporting.geojson` | 35 356 reporting points |
| `airports/runway.csv` | Runway thresholds, bearings, lengths, elevations |
| `airports/Airport_with_AP_Main.csv` | Airport table incl. the `Main` flag |
| `airports/gateway.geojson` | 689 stands/gates |
| `bangkok_fir_holdings_airac2607/…geojson` | 231 published holds — inbound course, turn, leg time/length, speed, altitude band |

The holdings drive the CD&R **HOLD** resolution; every parameter is taken
verbatim, and this layer is still on AIRAC **2607** (one cycle behind the rest).

## D. Thai APM — aircraft performance

`trajectory_sim/data/thaiapm_bada.sqlite` (+ an equivalent CSV export),
version `thaiapm-202607`, **66 aircraft types**, single ISA+15 variant.

Fitted to Bangkok FIR Mode-S DAP surveillance (`sur_air`, aggregate run 3193,
generated 2026-07-05). It is laid out like a BADA PTF but is **not a EUROCONTROL
product** — see `trajectory_sim/data/DERIVABILITY.md`.

What the simulator actually uses, and what it deliberately does not:

| Item | Used? | Note |
|---|---|---|
| Climb / descent **ROCD** (`rocd_nom`) | **Yes** | The p50 typical rate, used as-is even outside the brief's 1500–2500 fpm planning band |
| `rocd_lo` / `rocd_hi` | No | Percentiles across flights, **not** BADA mass bands, and inverted for climb |
| PTF TAS columns | No | Project-lead decision: the operational CAS/Mach schedule is used instead (source F) |
| Fuel columns / OPF coefficients | **Absent** | Not derivable from surveillance; there is no fuel model |

**Two consequences worth knowing.** Climb tables stop at the highest FL actually
observed in Bangkok, so a flight filed above that is *clamped* there rather than
extrapolated — an AT76 tops out at FL180 although its service ceiling is FL250.
And this dataset **superseded the BADA 3.16 PTF**; docstrings that still say
"BADA" are describing the shape of the table, not the source.

## E. CAT062 surveillance — measurement and validation

| File | What it is |
|---|---|
| `web/Data/cat062_20251223.csv` (256 MB, gitignored) | Raw ASTERIX CAT062 track sample — the measurement base |
| `scripts/data/thai24h_profile.json` | A day's traffic profile derived from it |
| `web/public/data/airports/runway_default.csv` | Runway actually used per airport per month |
| `trajectory_sim/data/cat62_reference.json` | Flight-time references per city pair |

`runway_default.csv` is a **climatology**: all available years pooled into twelve
month-of-year buckets, split arrivals/departures. Source table
`flight_data.runway_default` in the local PostgreSQL (`temp`), rebuild definition
`atc-traffic-dashboard/sql/fn_build_runway_default.sql`; prepared by Pongabha
Abhakara, Cat Analytics, 2026-08-07. It describes **what happened, not what the
AIP preferential-runway system says should happen.**

`cat62_reference.json` currently holds only **two** pairs — `VTBS-WMKK` 128 min
(the spec example) and `VTBS-VTSP` 60 min (the brief's own figure, and the graded
validation pair). Every other pair is checked against a derived estimate and
flagged `source="estimate"`.

## F. Operational assumptions — defined in code, not a dataset

These are **not** from any dataset and should not be presented as measured:

- **CAS/Mach speed schedules** (`performance.py`, 23 types) — "operational
  (airline LRC), calibrated to CAT062 tracks". Nominal BADA-style speeds run
  faster than real ops, so the schedule is operational by choice.
- **Service ceilings** — manufacturer-published, per type.
- **CAS→Mach crossover altitudes** — BADA convention (~FL280 narrow-body).
- **250 kt below FL100** restriction.
- **Separation minima** — 3 NM inside the Bangkok TMA, 5 NM elsewhere.

`icao-doc-4444-air-traffic-management.pdf` (ICAO PANS-ATM) is kept locally as the
procedural reference. It is copyrighted and gitignored.

`fir.geojson` (292 worldwide FIR boundaries) is a basemap layer whose upstream
provenance is not recorded in-repo; it is used for display only.

## Overlaps

Four places where the naive reading is wrong.

**1. `aip_VT.json` is not purely AIP.** The ENR 4.4 scrape yields 344 fixes, but
the file holds **609**. `scripts/complete_navdata.py` merges 265 more from the
GIS layers, because ENR 4.4 misses fixes real filed routes use — the VTBD/VTBS
arrival IAWPs (NAKON, WILLA, SEHNA, TUMGA…) among them. **241 of those exist only
in `aixm/star_waypoint.geojson`**, so roughly 40 % of the resolvable waypoint
coordinates are AIXM-derived despite the filename. The merge is additive and
idempotent: where ENR 4.4 publishes a fix, the AIP coordinate wins.

**2. A PDR is assembled from two sources.** AIXM supplies **when** each area is
active; `sectors_corrected/pdr.geojson` (ENR 5.1) supplies **where** it is and
**how high**. They are joined on designator, with a wrinkle: AIXM splits six
areas into lettered sub-areas (VTD21A1/A2/A3) that the GeoJSON keeps as one ident
plus an `areacode`. No match → `activity: null` → treated as permanently active,
the safe reading.

**3. Routes are split by function.** Fix sequences come from AIP ENR 3.1/3.3;
predefined plans from AIP ENR 1.10; segment **direction and level bands** from
AIXM. Only the first actually generates a trajectory.

**4. Two files can share a name.** `star_waypoint.geojson` under `aixm/` is the
live one. The superseded DFD copies under `data/{sid,star,pbn,ils}/` were deleted
on 2026-09-19; anything still referring to them is stale.

### Not modelled at all

- **No wind.** The trajectory model is zero-wind: `gs_kt == tas_kt`. A wind layer
  can be slotted in, but no weather data is ingested.
- **No fuel.** The Thai APM carries no fuel columns.

## Currency

| Dataset | Cycle | Effective |
|---|---|---|
| AIP scrape (`aip_VT.json`, `aip_routes_VT.json`) | 2609 | 03 Sep 2026 |
| AIXM export + everything derived from it | 2608 | 06 Aug – 02 Sep 2026 |
| Sector vertical-limit corrections | 2607 | 09 Jul 2026 |
| Bangkok FIR holdings | 2607 | 09 Jul 2026 |
| Thai APM | `thaiapm-202607` | generated 05 Jul 2026 |

**AIRAC 2609 took effect on 03 Sep 2026. The AIP half is on it; the AIXM half
(SID/STAR/approach layers, route-segment direction, P/R/D activity times) is one
cycle behind** until a 2609 SWIM export is ingested. The app already knows: the
PDR panel compares the activity data's `validTo` against the current date and
shows a staleness banner — that banner is about the AIXM half, so re-ingesting
the AIP does not clear it.

**What the 2609 AIP scrape changed** (ingested 2026-09-20):

- ENR 4.4: three new fixes (AVLOP, BEVKU, ISKIV); the stray `VTBS` "waypoint" the
  2608 file carried is gone (an aerodrome, not a fix — it sits on no airway).
- ENR 3.1: new airway L770 (NAN–AVLOP); W26 now runs …KADAV–ISKIV–BEVKU–IGPOP…
  (TK removed).
- ENR 1.10: 684 → 680 routes. The four VTBD/VTBS→VTPT routes via TK are no longer
  published; the two →VTPM routes via TK now read `…DCT BEVKU W26 KADAV`.
- ENR 5.1 (P/D/R areas) is unchanged from 2608 apart from the page's date stamp,
  so the AIXM 2608 activity times still describe the same areas.
- ENR 2.1 was amended for the Bangkok TMA (10-sector breakdown, frequencies). Its
  shape (50 NM about VTBD) and limits (3000 ft – FL160) already match
  `sectors_corrected/tma.geojson`, which is why that layer was not touched.
- `ingest_aip_routes.py` used to read text an amendment REMOVED (`<del>`) as if it
  were still part of the route, gluing "BEVKU" and "TK" into a fix called
  `BEVKUTK`. It now skips `<del>`; `tests/test_ingest_aip_routes.py` pins it.
- Not refreshed by any script: `thai_aip_ad2_thr_elevations.csv` and the
  `sectors_corrected/` vertical limits (corrected by hand against ENR 2.1 / 5.1).

The API caches the AIP file for the life of the process (`_aip()` in
`api/server.py`), so a running API has to be restarted to see a new cycle.

To move the AIXM half to 2609, against a fresh 2609 SWIM export:

```bash
python scripts/ingest_aixm_procedures.py       --input aixm_export_2609_VT_v5.1.1.xml
python scripts/ingest_aixm_route_segments.py   --input aixm_export_2609_VT_v5.1.1.xml
python scripts/extract_aixm_restricted_areas.py --input aixm_export_2609_VT_v5.1.1.xml
```

The AIP half is redone with (both pull straight from `aip.caat.or.th`):

```bash
python scripts/ingest_aip.py --airac YYYY-MM-DD
python scripts/complete_navdata.py
python scripts/ingest_aip_routes.py --airac YYYY-MM-DD
```
